# Workspace file transactions

The Nova workspace layer supports bounded LSP file-operation preflight for create, delete, and rename, with did* notifications remaining the commit/reconciliation boundary.

## Contract

Clients negotiate `workspace.fileOperations.willCreate`, `willDelete`, `willRename`, `didCreate`, `didDelete`, and `didRename` independently. The server advertises matching `file:**/*.nova` filters only for the operations the client supports. `workspace/willCreateFiles` rejects canonical duplicate targets and collisions with exact server-known open or detached Nova identities; `workspace/willDeleteFiles` captures known open/detached sources and rereads detached inputs before publication. Both are pure preflight requests: they return `null` on success and never mutate documents, the workspace index, or the filesystem. `workspace/willRenameFiles` is a pure preflight request over the complete server-known Nova workspace: it captures canonical affected URI identities, open document snapshots, the combined open/detached workspace snapshot set, workspace-folder generation, and affected detached mappings. It rejects duplicate canonical destinations, unrelated open-document collisions, and destinations already occupied by detached indexed Nova files with `RequestFailed`; closed/open swaps inside the same moving batch remain valid. Detached inputs are reread before publication, and document/workspace/folder or disk drift returns `Content modified`. A valid preflight returns `null` because Nova currently has no import/module path edits to apply. `workspace/didRenameFiles` remains the commit notification.

A rename notification is treated as a live snapshot mutation. While an ordinary request is running, the runtime may dispatch the notification on the foreground mutation lane so requests captured from the old document/workspace identity fail their existing exact-snapshot guards instead of publishing against a renamed file.

For every open Nova source in one notification batch, `DocumentStore.rename_many()` preflights the full set before mutation. Source URIs and destination URIs must be unique, destination URIs may not collide with an unrelated open document, and URI swaps between documents participating in the same batch are supported. A rejected batch leaves every open document unchanged.

Successful rekeying preserves language id, text, and document version but creates new immutable `Document` identities under the destination URIs. Old URI keys are removed from syntax, symbol, semantic, diagnostic, workspace-symbol, and semantic-token-delta state. The Nova adapter then rebuilds the exact derived snapshot chain for each destination URI from the preserved content.

Workspace-folder scope is evaluated again at the destination. A file renamed outside the captured workspace remains an open local document with local Nova semantics, but it no longer contributes declarations/references to cross-file workspace tooling. Cross-file diagnostics are reconciled once after the complete batch, and workspace-wide refresh consumers observe one new workspace generation.

The server explicitly clears push diagnostics for the old URI. New diagnostics and navigation locations use only the destination URI. Semantic-token delta history is not migrated: result ids from the old URI cannot be reused as a delta lineage for the renamed document.

## Deliberate boundary

Create/delete/rename preflight covers editor-owned open identities, bounded detached Nova identities, and two bounded local-only evidence layers for supported `file:` URIs. Path-entry evidence uses one `lstat` to capture whether the target is missing, a regular file, directory, symlink, or other entry plus its metadata signature. Mutation evidence is created only when the immediate parent can actually be observed with `lstat`; that evidence records parent kind, metadata, and the process-visible `W_OK|X_OK` result without following a symlink parent. When such local parent evidence exists, create/delete require it to be currently mutable and rename requires both observed source and destination parents to be currently mutable. Missing or otherwise unobservable parents remain outside this authority layer rather than turning editor-owned `file:` URIs into guessed local filesystem claims. Both evidence sets are reprobed inside the same exact publication boundary, so parent metadata or access drift returns `Content modified`. This is a feasibility guard, not a filesystem authorization or transaction guarantee: it does not resolve ACL policy, credential changes, ancestor/symlink target identity, remote-provider authority, or TOCTOU between preflight and the client's later mutation. After the client commits an operation, `didCreateFiles` and `didDeleteFiles` own closed-index reconciliation while `didRenameFiles` additionally owns open-document rekey/rebuild. Filesystem watchers beyond the negotiated client-mediated provider, full ACL/credential-aware or atomic filesystem transactions, remote providers, symlink-target identity, and module/import path rewrites remain separate milestones.
